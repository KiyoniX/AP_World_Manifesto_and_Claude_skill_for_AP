# Emulated games (ROM or disc image)

The client is Python, inside the apworld, built on an Archipelago framework that talks to the emulator. Game changes,
when needed, ship as a patch generated by the world into the output directory and applied by the client to the
player's own ROM: the world never reads a ROM at generation.

## Pick the framework

| System | Framework | Notes |
| --- | --- | --- |
| NES, SNES, GB/GBC/SGB, GBA, N64, PCE (and other BizHawk cores) | `BizHawkClient` (`worlds/_bizhawk/`) | Preferred for new work; `--client bizhawk` template |
| SNES on hardware (FX Pak Pro), Snes9x, RetroArch bsnes | `SNIClient` (`worlds/AutoSNIClient.py`) + SNI | SNES only |
| GameCube / Wii | Dolphin + `dolphin-memory-engine` (PyPI, MIT) | See Metroid Prime AP's `DolphinClient.py` |
| PS2 | PCSX2 PINE socket (port 28011) | See Ratchet & Clank 2 AP (`pcsx2_interface/pine.py`) |
| Others (PSP, PS1, DS, 3DS) | No established AP framework found | BizHawk 2.10+ lists 3DS and PSP cores: unproven for AP |

## BizHawkClient

Read `worlds/_bizhawk/README.md`. The template (`assets/templates/client-bizhawk/client.py`) already does the loop:

- `validate_rom`: claims only the patched ROM, by comparing bytes the patch writes (a ROM name or magic).
- `game_watcher`: reads the flag block and the applied-item counter **in one request** (same frame), sends checks
  with `ctx.check_locations` (which filters already-sent ones), sends the goal once, and grants the next item with a
  `guarded_write` guarded on the counter's old value, so an item can never be written twice.
- Fill `LOCATION_FLAGS`, `GOAL_FLAG`, the addresses and `item_writes()` from `game-map.md`.

The counter must be **saved together with the items it counts**: put it in the game's save data as it lives in
RAM (the block the game copies to the save file when the player saves), in two bytes the patch reserves. A reset
without saving then rolls back both the items and the counter, and the items are granted again. Writing it straight
into battery SRAM instead loses items: the counter survives the reset, the items do not. Pokémon Emerald's client
keeps its counter in the in-RAM save block for this reason.

Every read and write is gated on a game-state byte that says "normal gameplay", so nothing is written on the title
screen, during loads or cutscenes; the template guards writes on it.

The patch also writes a magic value, the seed name and the slot name into the ROM: `validate_rom` claims only patched
ROMs, sets `ctx.seed_name` (CommonClient then refuses a server running another seed) and `set_auth` logs in to the
right slot. The world produces them in `generate_output` from `multiworld.seed_name` and
`multiworld.player_name[player]`.

Rules: use `guarded_read` / `guarded_write` for anything at a moving address; avoid `lock` (it stutters); keep each
request bundle small; memory domain names differ between cores, so test every core the system offers
(`get_cores`).

## Patches

Archipelago's `worlds/Files.py` provides `APProcedurePatch` / `APTokenMixin` / `APDeltaPatch` for patches built from
token writes and bsdiff, applied by the client to the user's ROM. Study a world of the same system (e.g.
`pokemon_emerald`, `mm2`) before designing one.

## Finding addresses

- BizHawk's RAM Search and RAM Watch, and the hex editor: change one thing in game, filter on changed values, repeat.
- Existing knowledge: Data Crystal RAM maps (https://datacrystal.tcrf.net, search the game), decompilation projects,
  speedrun and TAS notes, existing randomizers. Credit and respect their licences.
- See `reverse.md` for the method and how to record proofs.

## Reference integrations (in the Archipelago repository)

GBA: `pokemon_emerald`, `mlss`, `cvcotm`. NES: `mm2`, `mm3`, `ff1`. GB: `pokemon_rb`, `marioland2`. N64: `cv64`.
